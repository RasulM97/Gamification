## Direction diagnosis and composition

The supplied screenshots show LTR form composition: title/labels at left, close
at right, first paired field at left. A saved explicit LTR preference reproduces
this orientation in Persian, even while all UI text is translated. The founder
could not confirm the setting used, so this is a reproduced explanation, not a
claim about their browser's stored state. That browser was not available through
the browser connector.

Auto still derives direction from locale; explicit LTR/RTL overrides remain
independent of language. The language menu now visibly reports the resolved
direction using existing translations and exposes selected locale/direction with
`aria-pressed`; its trigger exposes `aria-expanded`. A browser regression starts
with saved LTR, verifies its visible selected state, switches to Auto, then to
Hebrew and reloads: native RTL persists. No business/local storage is cleared by
the product changes.

Document direction synchronizes before paint. Shell and shared modal/drawer
boundaries explicitly use the resolved UI direction, so authored descendant
direction does not define system composition. User-authored fields retain
N3.3's empty-UI-direction/populated-`dir="auto"` behavior.

Tasks now places its title and Create action in one header, and search/status/
sort controls in a separate full-width toolbar below it. Both directions share
the same DOM: search, status options, sort; natural wrapping keeps visual reading
and keyboard Tab order together. The title/action row is not squeezed by the
control cluster. No CSS `order`, `row-reverse`, duplicate RTL markup, business
sorting changes or enum reversal.

Canonical dialog rule: title/subtitle at inline-start, close at inline-end;
wizard Back at start and Continue at end. First paired field occupies inline-start.
Existing flex/grid direction handles form groups, audience choices, wizard steps,
card metadata, table headers/cells, notification actions and rows. Native select
arrows and search clear controls retain platform behavior. Chromium's date picker
indicator is explicitly positioned at logical inline-end; native date segment
order stays LTR, and RTL fields align the segment group at the right. Native date
keyboard entry/value serialization remains unchanged.

Segmented buttons expose selection through `aria-pressed`; the N3.3 moving
indicator continues to follow selected bounds across direction, font and width
changes. Native buttons retain DOM Tab/Shift+Tab order and Enter/Space activation;
they are not falsely presented as ARIA tabs requiring a different keyboard model.

Media continues to use N3.3's bounded, bidi-isolated attachment cards and native
open/download behavior. No image/video mirroring, aspect-ratio change, new player
or new upload behavior. Font files and script-specific stacks are unchanged.
