## Changes and retry contract

* `mutate` separates service/flush rollback from commit exceptions and response
  serialization. A commit exception returns `503 OUTCOME_UNKNOWN` and retains
  staged bytes. A failure after confirmed commit returns `503 COMMAND_COMMITTED`.
* A new additive `command_receipts` table binds a committed identity to company,
  authenticated actor and a server-computed request fingerprint. A per-identity
  transaction advisory lock serializes duplicate deliveries. Receipt and domain
  writes commit together. Same key/same payload returns fresh authorized state
  without re-executing; changed payload returns `409 COMMAND_KEY_CONFLICT`.
  No stored response payload, token, file contents or economic rule is added.
* Organization, capability, account, task and wallet locks are retained in their
  original relative order. The retry lock is additional, not a substitute.
  Authentication runs on every delivery. Replay performs no new economic act.
* Mutation request headers accept `Idempotency-Key` on the legacy `/api` router.
  A safe retry MUST reuse the same key and exact request contents. Unkeyed
  requests retain their old API compatibility; repeated unkeyed POSTs or new
  keys are new commands, **not protected retries**. External/headless clients
  must retain keys across response loss. No blanket exactly-once HTTP claim.
* The web client supplies keys for task, redemption, reward/category and admin
  adjustment commands, retaining only hashed request/actor metadata and a random
  identity in sessionStorage before sending. Same-tab reload and renewed login
  for the same actor retain the identity. Changed details on an unresolved
  operation are blocked; no automatic mutation retry is introduced.
* A later auth failure does not erase an uncertain identity. A domain refusal
  after obtaining the retry lock and finding no receipt can explicitly confirm
  `commandOutcome: NOT_COMMITTED`, allowing corrected input. A successful retry
  completes the identity. Clearing browser storage or deliberately using a new
  tab/key is not recovery of an existing operation.
* Requests have a 30-second client response timeout. This bounds waiting, not
  server execution. Mutation transport/parse errors remain unknown outcomes.
* Store dispatch exposes confirmed completion and rejects duplicate in-flight
  UI submissions. Task/economic dialogs retain their draft until confirmed
  success. Saving and uncertain/committed feedback is explicit; server alerts
  do not silently expire. New outcome messages exist in all ten locales.

The receipt model is tenant/actor-bound by a composite FK. No receipt expiry or
deletion service is introduced: removing receipts would remove retry protection.
Migration `ee04f0202601` follows `ee03b2c4d503`, changes no existing economic
rows, and refuses downgrade once receipts exist. Apply the migration before a
future coordinated backend/frontend rollout; no migration or deployment was
performed against founder/production data.

## Targeted verification

* `test_f02_outcomes.py`: real PostgreSQL writes plus labelled commit/response
  failures; concurrent redemption replay; changed-body conflict; actor isolation;
  unchanged employee denial; committed attachment preservation and cleanup of
  retry-only bytes. Initial redemption fixture lacked funds and was corrected;
  this was a test-fixture failure, not evidence of a product regression.
* `test_f02_migration.py`: actual upgrade/repeated upgrade, exact ledger-row
  preservation, empty downgrade/re-upgrade, populated downgrade refusal.
* `f02.test.ts`: lost/truncated responses, stable identities across module reload
  and renewed session, changed-input blocking, storage failure before sending,
  refusal reconciliation and no automatic retry.
* `f02_ui.test.tsx`: mounted submit dialog retains draft during pending/unknown,
  double click sends once, success closes once; outcome alert does not expire.
* Focused frontend run: **35 passed**, including existing presentation and locale
  parity checks. Backend results and final consolidated verification are in the
  RA-1.2 final report.

The TypeScript project check reports 13 existing diagnostics in untouched files;
the same command on unchanged main reproduces the identical diagnostics. They
are not repaired in this scope. Real commit-ack loss is still not claimed as
reproduced. Unknown commit bytes may remain orphaned when commit actually failed;
retaining them is safer than deleting committed attachments. Crash recovery and
operator reconciliation remain distinct from safe retry delivery.
