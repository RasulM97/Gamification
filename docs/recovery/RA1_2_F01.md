## Confirmed cause

Source references below distinguish the original base lines from fixed lines:

* At the base, `routes.py:109,195,224,248,273` defined five async endpoints:
  create, submit, handoff, reopen, reactivate. They called synchronous SQLAlchemy
  code in `stage_files` (`routes.py:65-85`) and `mutate` (`routes.py:43-62`)
  directly on the event loop.
* `organization/service.py:13-15` executes blocking PostgreSQL transaction-level
  advisory locks; `:26-35` obtains the organization EXCLUSIVE lock before task
  command account/capacity locks. `task_services.py:3,39-41` applies that guard.
* Bootstrap (`serializers.py:75,97`) checks scoped visibility through
  `task_access.py:10-18`, acquiring organization SHARED locks.
* Auth reads (`security.py:74-94`) start the request session's transaction.
  `db.py:32-37` closes that session during dependency teardown; a read transaction
  can retain its locks and pool connection until then. Mutations commit/rollback
  in `routes.py:50-52`; the refreshed state at `:62` can open a new read transaction.
* An async command waiting synchronously for organization X blocks the loop.
  Other requests cannot complete dependency teardown and release organization S.
  PostgreSQL fair queueing puts later S requests behind the waiting X, amplifying
  the stall. The pool is bounded at 10 + 5 connections (`db.py:14`).

Inspected Stage 2 run `stage2-20261020-c9c56df-7b31`, including raw E1, E1B,
E3 events and the closure review. E1 was VALID / DEFECT_OBSERVED / CONFIRMED:
3/3 bounded 12-second windows had three failed loop probes and no successful
probes, verified blocker chains, and successful matched claim controls.
E1B confirmed S → waiting X → later S fair queueing. E3 separately measured
15 occupied connections and four health failures with zero loop failures;
pool saturation is not interchangeable with the F01 event-loop freeze.
These findings agree with source; no alternate cause was substituted.

## Minimal fix and preserved contracts

The five handlers are now ordinary `def` functions, so FastAPI runs their
complete synchronous work in its worker pool. `stage_files` uses
`UploadFile.file.read()` there. It retains capability validation before reads,
attachment validation before storage, and the original mutation/cleanup sequence.
`_handoff_deadline_present` (`routes.py:227`) only reads the already parsed form:
it preserves the distinction between an omitted deadline and explicit clearing.
It performs no DB or session work.

No tasks/futures are introduced around a shared Session. Auth, handler execution
and dependency cleanup use the same request-scoped Session sequentially.
They may execute on different worker threads, as existing synchronous routes do;
the fix neither shares a Session between concurrent requests nor overlaps its use.
The installed FastAPI 0.116.1 dispatches sync handlers through `run_in_threadpool`
and runs yield-dependency exit with its independent exit limiter.

Organization lock identity, S/X modes, transaction scope and acquisition order
are unchanged. Upload commands still take capability S before command org X;
the service then reacquires capability S and takes its existing account/task/
capacity/wallet locks. No lock is removed, narrowed, bypassed or reordered.
`mutate`, `get_db`, service guards, authorization, economic writers, append-only
records, deduplication constraints and all migrations are unchanged.
Admin / Manager / Employee authority remains server-enforced.

## Remaining limits

Finite worker/connection pools can still cause queueing or E3-style health
degradation under saturation. No sizing, admission, timeout or health policy was
changed. Sync worker cancellation/client disconnection does not promise to cancel
an in-flight transaction; ambiguous-response/commit behavior remains unchanged.
The timeout regression covers a database lock timeout, not every disconnect or
network failure. Existing capability/organization lock-order edges remain as-is;
this patch makes no universal deadlock-exclusion claim.

F02/F03, ambiguous-commit/file cleanup design, E6 multi-file staging failure and
all unrelated reliability work remain outside scope. Authorization, organization
lock semantics, atomic rollback, append-only economic behavior and duplicate
payment protection are preserved. Await independent review before further work.
